"스트리밍이 빠르다"는 말은 많이 들었는데, 화면에서 실제로 어떻게 보이는지는 본 적이 없었습니다. 그래서 89초짜리 한국어 면접 답변을 하나 녹음해 여섯 가지 방식에 똑같이 흘려보내고, 각 방식이 **언제 무엇을 내놓는지** 기록했습니다.

한 줄로 줄이면 이렇습니다. **가장 빨리 글자를 띄운 스트리밍 두 곳은 PostgreSQL 을 틀렸습니다. 오디오를 길게 넣을수록 고유명사를 더 잘 맞췄지만, 그만큼 늦게 떴습니다.**

_오른쪽 세 칸은 그 단어를 철자까지 맞게 옮겼는지다. 시각은 오디오 시작을 0초로 잡았다_

- **가장 먼저 글자를 띄운 건 Deepgram 입니다.** 1.16초에 "안녕하세요."가 떴습니다. 다만 이건 아직 바뀔 수 있는 중간 결과이고, 확정은 3.32초에 왔습니다.
- **스트리밍 두 곳이 모두 PostgreSQL 을 틀렸습니다.** 조각이든 통째로든 오디오를 모아서 모델에 넣은 나머지 넷은 전부 맞췄습니다.
- **통째로 넣은 쪽이 가장 많이 맞췄지만 가장 늦습니다.** 처리는 4~8초면 끝나는데, 말이 다 끝날 때까지 시작을 못 해서 첫 글자가 90초를 넘깁니다.
- **"무음"은 여섯 중 다섯이 "모음"으로 적었습니다.** 문맥을 넓게 본다고 풀리는 문제도 아니었습니다. 같이 통째로 돌린 Qwen 도 틀렸습니다.

## 어떻게 돌렸나 {#setup}

같은 녹음을 16kHz 모노로 바꿔 여섯 방식에 넣었습니다.

**스트리밍 둘**은 오디오를 100ms 분량씩 보내고 100ms 쉬는 식으로, **말하는 속도 그대로** 흘려보냈습니다. 파일을 한꺼번에 밀어 넣으면 지연이 거의 0으로 나오는데, 사람이 말하는 상황과는 거리가 멉니다.

```python
for i in range(0, len(pcm), step):          # step = 100ms 분량
    await ws.send(pcm[i:i + step])
    await asyncio.sleep(0.1)                # 말하는 속도에 맞춘다
```

**5초 청킹 둘**은 배치 STT 로 실시간 자막을 흉내 낼 때 흔히 쓰는 방식입니다. 오디오를 쌓다가 700ms 무음이 나오면 자르고, 5초를 넘기면 마지막 1.5초 안에서 가장 조용한 지점을 찾아 자릅니다. 89초가 23개로 갈렸고, 무음에서 잘린 게 10개, 5초에 걸려 강제로 잘린 게 13개였습니다. 잘린 조각은 동시에 3개까지 모델에 보냈습니다.

**통째로 둘**은 89.45초를 다 받은 뒤 한 번에 넣었습니다. 그래서 첫 글자 시각은 89.45초에 처리 시간을 더한 값입니다. Qwen 은 3.9초, whisper 는 8.3초가 걸렸습니다. 오디오 길이 대비 각각 22.8배, 10.7배 빠르게 처리한 셈입니다.

로컬 넷은 M5 Max 맥북에서 돌렸습니다. whisper 는 [mlx-whisper](https://pypi.org/project/mlx-whisper/)로 [whisper-large-v3-mlx](https://huggingface.co/mlx-community/whisper-large-v3-mlx)를, Qwen 은 [mlx-audio](https://github.com/Blaizzy/mlx-audio)로 [Qwen3-ASR-1.7B-4bit](https://huggingface.co/mlx-community/Qwen3-ASR-1.7B-4bit)를 불렀습니다.

## 스트리밍 둘은 "어디서 끊을지"를 누가 정하느냐가 다릅니다 {#streaming}

둘 다 웹소켓으로 오디오를 흘려보내는 건 같습니다. 차이는 **문장이 어디서 끝나는지를 누가 판단하느냐**입니다.

### Deepgram 은 서버가 정합니다 {#deepgram}

`wss://api.deepgram.com/v1/listen` 에 오디오만 보내면 서버가 말이 끊긴 지점을 알아서 찾아 문장을 확정합니다. 끊는 기준(endpointing)은 기본값 그대로 뒀습니다. 여기에 `interim_results=true` 를 켜면, 확정 전이라도 **지금까지 들은 만큼의 추측**을 계속 보내 줍니다. 이번 실행에서 글자가 담긴 확정 결과가 25개, 중간 결과가 66개 왔습니다. 그 밖에 `punctuate=true` 와 `smart_format=true` 를 켰습니다.

말이 끝나고 확정 결과가 오기까지는 중앙값 1.23초였습니다. 그 1초 남짓을 중간 결과가 메웁니다. 위 화면의 회색 기울임 글자가 그것입니다.

### Cartesia 는 제가 정해야 했습니다 {#cartesia}

Cartesia 에도 서버가 알아서 끊어 주는 엔드포인트(`/stt/turns/websocket`)가 있습니다. 그런데 한국어를 쓰려고 `ink-whisper` 로 붙으면 연결이 바로 끊깁니다.

```text
websockets.exceptions.ConnectionClosedError:
  received 1008 (policy violation) Unsupported model
```

지금 Cartesia 의 주력 모델은 `ink-2`(영어)와 `ink-preview`(영어, 프랑스어, 힌디어, 일본어, 스페인어)이고, 한국어가 되는 `ink-whisper` 는 [이전 모델](https://docs.cartesia.ai/build-with-cartesia/stt-models/older-models) 목록에 있습니다. 요금표에는 `ink-whisper` 의 turns 단가도 적혀 있지만, 2026-09-23 에 `cartesia_version=2025-04-16` 으로 붙었을 때는 위처럼 거절됐습니다.

그래서 수동 엔드포인트(`/stt/websocket`)를 썼습니다. 여기서는 오디오를 아무리 보내도 결과가 오지 않습니다. **클라이언트가 `finalize` 를 보내야** 서버가 "여기까지가 한 문장"으로 보고 결과를 돌려줍니다.

```python
while cuts and sent_ms >= cuts[0]:   # 끊을 시각이 되면
    await ws.send("finalize")        # 여기까지 확정해 달라고 알린다
    cuts.pop(0)
```

오디오는 실시간으로 흘려보내니 전송은 스트리밍이 맞습니다. 하지만 끊는 판단은 클라이언트 몫입니다. 비교 조건을 맞추려고 5초 청킹이 자른 것과 같은 시각에 `finalize` 를 보냈습니다.

첫 결과가 5.17초에 온 이유도 여기 있습니다. 첫 조각이 5초 상한에 걸려 잘렸고, 그 시각에 보낸 첫 `finalize` 에 0.17초 만에 답이 왔습니다. 이번 실행에서 받은 결과 37개는 전부 확정 결과였고, 그중 7개는 빈 문자열이었습니다.

## 중간 결과는 틀렸다가 고쳐집니다 {#interim}

Deepgram 의 중간 결과는 말이 이어질수록 계속 바뀝니다. 첫 문장은 이렇게 흘러갔습니다.

```text
1.16s  중간  안녕하세요.
2.15s  중간  안녕하세요. 저는 맥엔드
3.12s  중간  안녕하세요. 저는 백엔드 개발을 주로 해야
3.32s  확정  안녕하세요. 저는 백엔드 개발을 주로 해학
```

"맥엔드"는 뒷말이 들어오면서 "백엔드"로 고쳐졌습니다. "쿠번에"가 "쿠버네티스에"로, "두 배"가 "두 대로"로 바뀐 자리도 있었습니다.

반대로 **확정이 중간보다 나빠진 자리도 있습니다.** 실제 발화는 "해 왔고"였는데, 중간 결과 "해야"가 확정에서 "해학"이 됐습니다. 51초 무렵에는 중간 결과에 "웹 소켓 연결이 자꾸"까지 있었는데, 확정은 "가장 어려웠던 건 웹"과 "연결이 자꾸 끊기는 문제였습니다" 둘로 나뉘면서 "소켓"이 빠졌습니다. 중간 결과를 화면에 띄우는 건 빠르게 보여 주는 대신, 사용자가 글자가 바뀌는 걸 보게 된다는 뜻입니다.

## 문맥이 짧으면 어디가 무너지나 {#accuracy}

### PostgreSQL

```text
원문        주로 쓴 스택은 FastAPI와 PostgreSQL이고요
Deepgram    주로 쓴 스택은 fast API와 first Gras Ql이고요.
Cartesia    주로 쓴 스택은 FastAPI와 버스 그레스 퀘이고요
```

나머지 넷은 전부 `PostgreSQL` 로 적었습니다. 같은 경계에서 끊은 Cartesia 와 5초 청킹 + whisper 가 갈렸으니, 경계만으로 설명되지는 않습니다. 모델 차이도 섞여 있는 것으로 보입니다.

### 숫자와 단위

"팔백 밀리초", "삼백 밀리초"를 한글로 읽었습니다.

```text
Deepgram          800 밀리초였는데 300 밀리초까지 내렸고요
Cartesia          800mS였는데 300mh까지 내렸고요
청킹 + whisper    800ms였는데 300ms까지 내렸고요
```

Cartesia 가 `300ms` 를 `300mh` 로 적었습니다. 숫자는 맞고 단위만 틀려서 **읽는 사람이 틀린 줄 모르고 넘어가기 쉬운** 종류입니다.

### 말을 고치는 자리

원문은 "두 대로 버텼습니다. 어, 그게… 아니 정확히는 두 대가 아니라 세 대였네요."입니다. Deepgram 만 뒤쪽을 "세 **개**였네요"로 적었고 나머지 다섯은 "세 대"로 맞췄습니다.

### 무음과 모음

"**무음** 구간을 찾아서 자르는 방식으로"를 whisper 통째로만 맞췄고, 나머지 다섯은 전부 "**모음** 구간"으로 적었습니다. 발음이 거의 같아서 앞뒤 뜻으로만 구별되는 단어입니다. 오디오를 다 들은 Qwen 도 틀렸으니, 문맥을 늘리는 것만으로는 안 되는 자리입니다.

### LiveKit

철자까지 맞춘 건 Qwen 통째로(`LiveKit을`) 하나였습니다. 나머지는 "라이브 킷", "라이브킷", "라이브. 킷", "라이브... 킷"이었고, Cartesia 는 "킷"을 아예 빠뜨렸습니다.

눈여겨볼 건 **같은 Qwen 이 5초로 잘라 넣으면 틀렸다**는 점입니다. 한 번에 들려준 오디오의 길이가 결과를 갈랐습니다.

## 그래서 무엇을 고르나 {#choose}

우열을 가릴 실험은 아니었습니다. 다만 무엇을 포기하고 무엇을 얻는지는 분명하게 보였습니다.

- **말하는 동안 자막이 떠야 한다면** 중간 결과를 주는 스트리밍입니다. 대신 글자가 바뀌는 게 보이고, 고유명사는 틀릴 각오를 해야 합니다.
- **고유명사와 숫자가 중요하다면** 모델부터 직접 대 봐야 합니다. 같은 경계로 잘라도 모델에 따라 PostgreSQL 이 갈렸고, LiveKit 은 통째로 넣은 Qwen 하나만 맞췄습니다.
- **둘 다 필요하다면** 두 경로를 같이 둘 수 있습니다. 말하는 동안에는 스트리밍으로 보여 주고, 끝난 뒤 녹음 전체를 한 번 더 돌려 확정본으로 바꾸는 방식입니다. 이번 녹음 기준으로 통째 처리는 4~8초면 끝났습니다.

## 읽을 때 감안할 것 {#caveats}

- **표본이 하나입니다.** 한 사람이 한 번 녹음한 89초로 서비스나 모델의 우열을 말할 수는 없습니다.
- **조건이 같지 않습니다.** 스트리밍 둘은 네트워크를 거쳤고 나머지 넷은 제 맥북에서 돌았습니다. 5초 청킹은 보통 외부 API 로 whisper 를 부르는데, 저는 같은 모델을 로컬로 돌려서 네트워크 왕복이 빠져 있습니다. 실제보다 빠르게 나온 값입니다. 같은 조건에서 모델만 바꾼 두 청킹끼리는 비교해도 됩니다.
- **정확도는 눈으로 봤습니다.** 오류율(CER) 같은 수치는 재지 않았고, 대본에 심어 둔 단어를 맞췄는지만 확인했습니다.

## 비용 {#cost}

2026-09-23 에 각 요금 페이지를 보고 적었습니다.

- **Cartesia**: `ink-whisper` 실시간은 오디오 1초에 1크레딧입니다. 무료 플랜이 매달 20,000 크레딧을 주니 한 달에 5시간 33분입니다. 말이 없는 구간도 연결된 시간만큼 빠집니다. ([요금 안내](https://docs.cartesia.ai/pricing))
- **Deepgram**: 가입하면 $200 크레딧을 줍니다. Nova-3 단일 언어 스트리밍은 지금 분당 $0.0048 인데, 이건 기간 한정 할인가이고 정가는 $0.0077 입니다. $200 이면 할인가로 약 694시간, 정가로 약 433시간입니다. ([요금 안내](https://deepgram.com/pricing))
- **로컬**: 모델만 받으면 돈이 들지 않습니다.
